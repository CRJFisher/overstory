Drift sync lifecycle

How a human-authored functionality tree, its bindings to code, and the code itself are kept in agreement as any of the three changes. Each chart shows one part of the loop; the colour of a step says who decides. The last two sections say where the loop is mechanical, where it rests on judgment, and whether that makes it precarious.

1. The loop at a glance

Three things change: the code, the tree, and plan branches that carry both. Whatever changes, the same loop runs. Detection is deterministic and produces a set of suspect nodes, each with its reason. An agent drafts one proposal per suspect. Proposals surface where the author already is, and the author's verdict is the only thing that changes the tree's words. Every verdict is kept as a golden case, so detection and drafting are tuned by the record rather than re-argued.

The invariant that makes the loop safe to automate: the tool rewrites link targets, never node text. Anything mechanical can be applied without asking. Anything that touches the author's words is a proposal.

2. Code changed: routing a diff to the tree

This is the direction with no human who already knows the answer, so it carries the most machinery. The first three questions are mechanical. What each branch ends in is the interesting part: a dead binding is a fact, but whether a capability is still true after its code was edited is not decidable from the diff. The loop bounds where to look and leaves whether to judgment.

Fragile point: the closure depth. Direct bindings miss a behaviour change in shared code two calls down. Full call-graph closure marks everything that depends on a utility module. Depth k is the precision dial of the whole loop: too wide and the author drowns in false suspects; too narrow and drift lands silently. A test-bound leaf sidesteps the dial, because the test exercises the closure for you.

3. Tree changed: from an author's edit to built code

The author knows what they meant, so the machinery here is light: a fingerprint over the load-bearing text separates wording from functionality, and a functionality change becomes a plan by construction. The plan is not a second document. It is the tree edited on a branch, and the overlay is the diff. The branch may merge only when its nodes bind, so the canonical tree on the main branch never describes code that does not exist.

Fragile point: identity across restructuring. A git diff of a markdown outline cannot tell a moved node from a deleted one plus a new one. Without a stable id per node, every restructure breaks bindings and makes the overlay unreadable. With ids, the file carries machine-written marks the author must tolerate. This is one decision, and three features hang on it: the computed overlay, the metadata sidecar, and per-reader state.

4. A node's life

Every node is in exactly one of four states, and the transitions are the events from the two charts above. The state is the thing the overlay renders and the anti-rot sweep counts.

stateDiagram-v2
  [*] --> Planned: author writes a node the code does not yet satisfy
  [*] --> Built: author writes a node and binds it to existing code
  Planned --> Built: binding resolves and its test passes
  Planned --> Retired: plan abandoned
  Built --> Suspect: bound code edited, or binding dead
  Suspect --> Built: author ratifies keep or reword
  Suspect --> Retired: capability removed
  Built --> Planned: author changes load-bearing text and the code must follow
  Retired --> [*]
A Suspect node is still rendered as true. Its truth is simply older than the code. How long nodes sit in Suspect is the one number that says whether the loop is working.

5. Ratification: the throughput constraint

Every direction ends at the same place. The mechanism removes the labour of noticing and drafting, not the labour of deciding. So the loop has a budget, and two ways to blow it: proposals that pile up unratified, and proposals accepted verbatim until the tree is no longer in the author's words.

Fragile point: the tree's truth is only as fresh as its last ratification. Nothing in the mechanism can make the author decide faster. What the mechanism can do is keep the queue small, keep each item one keystroke, and put it where the author is already looking. Whether that is enough is measurable before anything is built: replay a repo's recent commits through the detection rules by hand and count suspects per commit.

8. Verdict: is the syncing lifecycle precarious?

It is mechanical wherever the question is "does this still exist", and it rests on judgment wherever the question is "is this still true". The three red rows are one difficulty, the semantic gap, and the loop handles it the only way it can: bound where to look deterministically, draft the answer, and let the author decide. That is sound. It is precarious only in the sense that its precision is a dial, not a guarantee.

  • The dial is closure depth, and it decides both failure modes at once. It can be tuned from evidence rather than taste: replay a real repo's history, count suspects per commit at each depth, and count the drifts each depth would have missed.
  • The one lever that moves the boundary is test binding. Where a capability names its test, "still true?" becomes "does CI pass?", renames stop mattering, and the closure is exercised for free. Its cost is honest: functionality without a test is unbound, and the tree says so.
  • Completeness is the weakest link, because no binding can detect what the tree never said. Entry-point and test heuristics catch the common case; a periodic sweep is the backstop.
  • Ratification is the throughput constraint. The mechanism removes noticing and drafting; deciding stays with the author. The tree is exactly as true as its last ratification, and the design's job is to keep the queue inside a budget: apply the mechanical, rank the rest, and surface it at the edit.
  • Why this is not the decay the literature measured. Every population in that research updated by hand, far from the code, with nothing proposing the repair. Here detection is mechanical, the draft is produced at the edit, and the human's part shrinks to a verdict. The research's conditions for survival, an update that is small, adjacent, and rides an existing step, are met by construction, so long as the verdict itself stays cheap. That is the number to measure first.

9. What to build first, given all this

  • The deterministic layer alone, with no agent: resolve bindings, mark touched bindings to depth k, flag unbound entry points and tests, check anchors. It is small, it has ground truth, and it produces the two numbers the whole design turns on: suspects per commit, and drifts missed.
  • Replay before you build. Run those rules by hand over the catalog repo's last thirty commits. If the suspect count per commit is a handful and the misses are rare, the loop is not precarious. If either number is bad, the fix is in the binding primitive or the depth, and it is better learned on paper.
  • Bind the catalog three ways, symbol, anchor, and test, on one subject, so the primitive is chosen from the replay rather than argued.
